# ADR-016: Code editor component

## Status
Accepted (M9.06). Supersedes the "minimal editor" parts of ADR-002 and the multi-line editor paragraph of ADR-011. Changes SPEC §17.3 and §17.11 (Tab in code editors, the new keys, completion menu behaviour).

## Context
Every multi-line surface (Body, "Open as text", Scripts, Tests, the WebSocket composer, Environment bulk edit) drew its own lines from `EditorState`, took characters from key events (no IME), laid out every line each frame, assumed a fixed 7.8 px column, and inserted two spaces on Tab. Docs was static text.

## Decision
- **Build, don't adopt.** `CodeEditor` extends Fluxwire's own editor on `gpui =0.2.2`. GPUI Kit's Editor is the behaviour reference (builder options, keys); `gpui-component` still needs `gpui-pre 0.3.9` (ADR-001, ADR-002).
- **Component API.** `CodeEditor` is an entity with its own `FocusHandle`, scroll and caret. Builder: `language`, `line_numbers`, `soft_wrap`, `tab_size`, `show_whitespace`, `indent_guides`, `auto_close`, `read_only`, `placeholder`, `completion_provider`, `read_only_ranges`. Events: `Changed`, `Focused`, `Blurred`, `CaretMoved`. Defaults come from `[editor]` in `settings.toml` (`EditorSettings::for_language`), applied at creation, when the language changes and on settings reload.
- **Pure logic is separate and tested without GPUI:** `display_map.rs` (offset ↔ row/column, soft wrap, tabs), `language_config.rs` (pairs, indent rules, comment tokens), `code_editor_ops.rs` (each edit is a `Plan`: one replacement plus the selection afterwards), `markdown_edit.rs`, `completion.rs`, `completion_providers.rs`, `docs_edit.rs`.
- **IME.** Text arrives only through `EntityInputHandler`, copied from `text_input.rs` (UTF-16 ranges, marked range underlined). Movement, clipboard and undo reuse the `TextInput` actions (key context `TextInput CodeEditor`), so `keymap.toml` rebinding applies. The guard test no longer needs an allow-list entry for the editors.
- **Document sync.** The document (`OpenDoc`, `EnvDoc` bulk buffers, `Composer::text`) owns the text. `WorkspaceView::code_editor` creates one editor per (request, surface) and, on every draw, pushes the document text in when it differs. A trailing newline the span editor normalises away does not count as a difference. Edits arrive as `Changed` and go through `set_target_text`, i.e. the span editor, so form views and "Open as text" stay one document and sending never requires saving. Each plan is one undo step (`TextBuffer`); an outside `set_text` clears undo, as before.
- **Tab ownership.** SPEC §17.11 gave Tab to the owner of a field. A code editor is a multi-line editor and takes it: Tab accepts an open completion, otherwise indents (block-indents a multi-line selection); Shift+Tab outdents. Enter, Tab and PageUp/PageDown are read from key events; every other editor key is an action in the `CodeEditor` context (`editor: …`), hidden from the palette except `go to line…`, `toggle soft wrap` and `request: format body`. Esc is an action that closes the completion menu and otherwise propagates, so the owner's Esc (cancel) still works.
- **Rendering.** `code_editor_element.rs` shapes and paints only the rows in view, with a gutter, current-line highlight, selection (dimmed when unfocused), blinking caret and the IME marked range. The font is monospace, so a column is one measured cell; hit-testing and Up/Down use the display map, not shaped text.
- **Completions.** `CompletionProvider` is synchronous (`completions(text, offset, trigger)`), because providers only read the text and small tables; the editor recomputes on every keystroke, so a result can never be stale. Providers compose in order (earlier ranks higher, labels deduplicated): variables (only answer inside `{{`), the surface's own, buffer words (skipped over 200 KB). Ranking uses nucleo. The `fw` symbol table is read from the embedded `fw.d.ts` (`fluxwire-script/src/completions.rs`) and a test pins the `pm` table to `pm.js`; scripts are never run or transpiled for completion. A line scanner reads `fw.d.ts` because the generated file is regular; oxc is not needed.
- **Docs modes.** The Docs sub-tab has two modes per tab, *Preview* (default) and *Source*. Preview renders the Markdown with GPUI elements (`markdown_view.rs`: pulldown-cmark events to a block model; `docs_preview.rs`: headings, inline styles, links that open in the browser, lists and task lists, quotes, tables, rules, highlighted code blocks); it is read-only, and the chip on a request block opens the owning sub-tab. This brings forward part of the Docs Preview that M13 would have delivered; Split, generated sections and export stay in M13. *Source* is the editor below.
- **Docs editor.** Source mode edits the file after the front matter in a Markdown `CodeEditor`. Front matter and recognised fences are read-only ranges (`docs_edit::protected_ranges`). Changes go through `fluxwire_format::edit_prose`, which refuses any edit touching front matter or a recognised fence and reports an edit that would create one; property tests pin byte-identity of everything else.
- **Settings.** `[editor]` keys: `tab_size`, `hard_tabs`, `soft_wrap`, `show_whitespace`, `indent_guides`, `line_numbers`, `auto_close`, `cursor_blink`, with `[editor.languages.<json|xml|yaml|ts|js|markdown|text>]` overrides. Bad values fall back with a notice.

## Consequences
One editing core remains; `EditorState` is gone and `editor.rs` keeps only the read-only `code_view` and token colours. Single-grammar languages (JSON, YAML, JS, TS, XML) highlight incrementally (`highlight::Highlighter`: `Tree::edit`, re-parse from the old tree, spans only for the rows in view). Measured in release on a 1 MB JSON body: first parse 80 ms, then at most 5.3 ms per typed character for the update plus visible spans, against 119 ms for the old whole-buffer highlight. `.flux.md` and plain text still use a whole-document pass per revision, and the display map is rebuilt in full per edit, so whole-editor frame time on very large files is not yet measured. The editor draws indent guides, whitespace markers (`show_whitespace`), boxes around a matching bracket pair, `{{var}}` references (accent when they resolve, error colour and underline when not; Body and "Open as text") and, in Docs, muted read-only text, a gutter bar and a right-aligned chip per protected block. Editor colours are theme tokens (`editor_active_line`, `editor_indent_guide`, `editor_invisible`, `editor_bracket_match`: Zed keys `editor.active_line.background`, `editor.indent_guide`, `editor.invisible`, `editor.document_highlight.bracket_background`, optional in Zed JSON, `[ui]` keys of the same names in microterm TOML, derived from the existing tokens when absent). Clicking a Docs chip opens the owning sub-tab (Body, Scripts, Tests, or Open as text). Not yet done: the editor context-menu items.

## Deferred
Find and replace, folding, multi-cursor and column selection, inline diagnostics, hover tooltips, go-to-definition, a language server or type checking, JSON Schema-driven completion, a minimap, Docs Preview/Split and rendered Markdown (M13), Vim mode, persisting the soft-wrap toggle, an `[editor]` settings writer.
